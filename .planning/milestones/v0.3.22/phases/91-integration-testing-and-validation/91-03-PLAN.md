  <action>
    Create a new `describe('autopilot v2 E2E — two-phase parallel pipeline', ...)` block near the end of the test file (before the closing of the top-level describe).

    **Test scenario:** Two independent phases (48, 49) with no dependency between them and no file overlap. Both execute in parallel worktrees, both go through the 4-step post-phase pipeline, and merge in arrival order via a shared merge queue.

    **Setup (beforeEach or inline):**
    - Create autopilot fixture using `createAutopilotFixture()` — this sets up a tmp dir with ROADMAP.md, config.json, STATE.md, and phase directories
    - Create PLAN.md files for both phases in the fixture (with `files_modified` frontmatter and basic task structure)
    - Mark both phases as planned (write `{phase}-planned.json` status markers)

    **Mocks needed — ALL git and gh operations must be mocked:**
    1. `childProcess.spawn` — mock to return successful `createMockChild(0)` for all subprocess calls (execute, simplify, code-review). Track call count per phase to verify correct number of spawns.
    2. `childProcess.execFileSync` — comprehensive mock handling:
       - `git worktree add` → create the directory (fs.mkdirSync) and return empty string
       - `git worktree remove` / `git worktree prune` → return empty string
       - `git push` → return empty string
       - `gh pr create` → return `https://github.com/test/repo/pull/N` (different N per phase)
       - `git rebase main` → return empty string (no conflicts)
       - `git rev-parse --abbrev-ref HEAD` → return `grd/phase-{N}`
       - `git push --force-with-lease` → return empty string
       - `gh pr merge` → return empty string; **record the merge order** (push phase number to an array when this is called)
       - `git diff --name-only` → return empty string (for write-intent comparison)
       - `git checkout` → return empty string
       - All other git commands → delegate to real execFileSync or return empty string
    3. `fs.existsSync` / `fs.readFileSync` — may need selective mocking for PLAN.md reading; use `jest.spyOn` and `.mockImplementation` with fallthrough to real fs for fixture paths
    4. Mock `spawnClaudeAsync` or the spawn pattern to simulate execution completing — phase 48 finishes first, phase 49 finishes second (use delay in mock to control ordering)

    **Test approach — prefer testing via `runPostPhasePipeline` + `createMergeQueue` composition rather than full `runAutopilot`:**
    The full `runAutopilot` function has many dependencies (config loading, phase resolution, worktree creation). Instead, compose the E2E test from the building blocks:
    1. Create a shared `mergeQueue = createMergeQueue()`
    2. Launch two `runPostPhasePipeline` calls concurrently via `Promise.all`, both using the shared mergeQueue
    3. Use `delay()` in mocks to make phase 48's Step 4 reach the merge queue first
    4. Assert both complete successfully
    5. Assert the merge order array shows phase 48 merged before phase 49

    **Alternative: if testing through runAutopilot is feasible** with the existing `createAutopilotFixture` and mock infrastructure, prefer that for true E2E coverage. The key requirement is that the test demonstrates:
    - Two phases execute
    - Post-phase pipelines run (simplify, PR, review for both)
    - Merge queue serializes the rebase+merge step
    - Phases merge in execution-completion order

    **Assertions:**
    - Both pipelines return `{ status: 'completed' }`
    - Both have `prUrl` set
    - Merge order array is `['48', '49']` (48 merged first)
    - spawn was called correct number of times (2 per phase for simplify+review = 4 total, plus execute spawns if going through runAutopilot)

    **Cleanup:** afterEach removes fixture dir, restores all mocks.
