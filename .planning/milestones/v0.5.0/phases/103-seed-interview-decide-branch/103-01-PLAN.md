    positioned BEFORE the existing `gd research $ARGUMENTS` invocation guidance (after the

    so the interview is understood as a pre-CLI step for a NEW thread only.

    Mirror the superpowers:brainstorming and plan-phase §9 clarification style (thin, no
    state machine). The protocol MUST specify:
    1. Trigger scope: run ONLY for a fresh `gd research "<question>"` start. Do NOT run on
       `resume <id>`, `status`, the `deep-research` mode branch, or when `--no-gates` /
       autopilot / a non-interactive context is in effect (in those cases invoke
       `gd research` with the original question unchanged).
    2. Context first: before asking anything, restate the user's question and identify the
       ambiguous dimension(s) that block a falsifiable experiment (what exactly is measured,
       against what baseline/target, under what conditions).
    3. ONE question at a time: call AskUserQuestion with a SINGLE multiple-choice question
       per call (options preferred over free text; offer a recommended-first option and an
       "other / let me specify" escape). Ask follow-ups one-by-one, not batched.
    4. Stop condition (hard): STOP asking the moment the refined question yields a
       FALSIFIABLE METRIC TARGET — i.e. a single numeric metric, a comparator (>=,<=,>,<,==),
       and a concrete target threshold the autoresearch loop can test. Do not over-interview.
    5. Once per thread: the interview happens exactly once, before the thread exists.
    6. Handoff: invoke `gd research "<refined question>"` passing the REFINED question as the
       argument. Preserve the ORIGINAL user question verbatim by echoing it to the user
       (e.g. "Original: …  →  Refined: …") so it is never silently discarded.

    Keep it thin: ask -> refine -> invoke. No answers file, no resume plumbing (that is the
    checkpoint protocol already documented in the "Interactive steering" section, which is a
    DIFFERENT, in-loop mechanism — cross-reference it but do not merge).
