<feature>
  <name>checkpoints.ts core plumbing</name>
  <files>lib/research/checkpoints.ts, tests/unit/research/checkpoints.test.ts</files>
  <behavior>
    Emit-time validation:
      valid checkpoint (≤4 questions, each with exactly one recommended:true) → returned unchanged, persisted, thread.pendingCheckpoint set, status 'paused'.
      5 questions OR a question with zero/two recommended options → ONE stderr warning + fall back to recommended-default resolution (no throw).
    checkpoints.jsonl: appendCheckpointRecord(dir, record) then readCheckpointLog(dir) → array in append order (mirrors ledger.jsonl; append-only, never rewritten).
    consumeAnswered(resumedCheckpoint, 'design', 1): returns the stored answers when (point,iteration) match; returns null otherwise (one-shot — a second call for the same point/iteration returns null).
    readInteractiveConfig(cwd):
      absent research_gates.interactive → { enabled:false, seed:true, hypothesize:true, design:true, decide:true, max_rounds:2, max_questions:4, hypothesis_candidates:3, every_iteration:false, fallback:'recommended' }.
      hypothesis_candidates:9 → clamped to 5 (+warning); :0 → 1 (+warning). max_rounds:0 → 2 (+warning). fallback:'bogus' → 'recommended' (+warning). max_questions non-number → 4 (+warning). Each emits ONE stderr warning naming the key.
    resolveInteractive(cfg, opts): {active:false} under opts.noGates | config.autonomous_mode | opts.autopilot/GRD_AUTOPILOT | opts.concurrency>1 | opts.nonInteractive; else {active: cfg.enabled}.
      NOTE (checker info): GRD_AUTOPILOT is a NEW env contract introduced by REQ-196 — it does not
      exist in the codebase today. resolveInteractive reads it via an injectable env accessor
      (opts.env ?? process.env) so tests stay deterministic; test BOTH branches explicitly:
      opts.autopilot:true with no env, and GRD_AUTOPILOT=1 via injected env with opts.autopilot absent.
  </behavior>
  <implementation>
    'use strict' first line; CommonJS module.exports; zero `any` (use Record<string,unknown> or
    the InteractiveConfig type from 101-01); typed requires. Create the sibling
    `lib/research/checkpoints.js` tsx-loader proxy (copy the exact one-line shape of an existing
    lib/research/*.js proxy).

    - emitCheckpoint(cwd, thread, ck, deps?): validate ck (helper validateCheckpoint returning
      {ok, reason}); on invalid → console.warn one line + return a resolved-to-defaults record
      (answeredBy:'default') WITHOUT pausing. On valid, if a checkpointHandler is injected
      (deps.checkpointHandler) call it; the DEFAULT handler pauses: set thread.pendingCheckpoint=ck,
      status='paused', saveThread, incrementCounter('research.checkpoint_pauses_total'), return the
      paused shape. (Emission WIRING into runLoop is Phase 102 — here the handler seam + default
      pause behavior are just built and unit-tested via injection.)
    - resolveCheckpoint(cwd, thread, ck, answers): stamp resolvedAt + answers, append to
      checkpoints.jsonl, clear thread.pendingCheckpoint. Missing answers for a question → resolve
      to that question's recommended option with answeredBy:'default' (the timeout behavior).
    - consumeAnswered(resumedCheckpoint, point, iteration): one-shot match on point+iteration.
    - checkpoints.jsonl IO: path = threadDir/checkpoints.jsonl; append via fs.appendFileSync of
      `JSON.stringify(record)+'\n'`; read by splitting non-empty lines (mirror ledger.ts).
    - readInteractiveConfig(cwd): raw JSON read of .planning/config.json (like readResearchGatesConfig
      at orchestrator.ts:121 — loadConfig drops unknown keys, so raw-read); apply the warn+clamp
      matrix; return a fully-populated InteractiveConfig.
    - resolveInteractive(cfg, opts): pure function, no IO, no config mutation.
    Inject the metrics incrementCounter (require('../metrics')) exactly as orchestrator.ts:11 does.
    Follow the DI style of spawn/runner injection (deps object with optional overrides).
  </implementation>
