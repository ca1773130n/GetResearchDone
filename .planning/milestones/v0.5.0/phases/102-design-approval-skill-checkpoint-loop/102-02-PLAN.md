  <files>commands/research.md</files>
  <action>
  Append a `## Interactive steering (human-in-the-loop)` section. Keep it THIN — a protocol,
  not a state machine (research §4 decision 6). Mirror plan-phase.md §9 clarification handling
  verbatim in spirit. Instruct the driving agent:

  1. `gd research "<q>"` and `gd research resume <id>` return machine JSON (the research
     subcommand outputs JSON by default). After each call, inspect `result.pendingCheckpoint`.
     If it is absent/null, the loop finished or gate-paused normally — handle as today.
  2. If `result.pendingCheckpoint` is present: parse it FROM THE CLI JSON ONLY — never open
     thread.json or checkpoints.jsonl (R10: the payload is self-contained and version-safe).
  3. Call **AskUserQuestion** with all `pendingCheckpoint.questions` in ONE call (max 4). For
     each question list its `recommended:true` option FIRST, labeled "(Recommended)"; if a
     question has `freeform:true`, tell the user they may type contract edits
     (`metricKey/comparator/target/language`, one `key: value` per line). Run at most 2 rounds;
     de-dupe by question `ask` TEXT (NOT `id` — ids are per-round labels, not stable). After 2
     rounds, proceed with the recommended defaults.
  4. Build an answers object `{ "<questionId>": { "label": "<chosen option label>",
     "text": "<freeform text if any>" } }` and write it to a file (e.g.
     `.planning/research/threads/<id>/answers.json`) using the **Write tool** — never pass
     answer text through the shell/argv (R8).
  5. Resume: `gd research resume <id> --answers <that file>`. Re-inspect the returned
     pendingCheckpoint and repeat only if a NEW checkpoint (different point/round) is emitted
     (e.g. after a "Revise").

  Add a one-line pointer under `## Subcommands` that `resume` accepts `--answers <file>` for
  interactive checkpoints, and note `gd research status <id>` shows pending questions for
  manual answering. Do NOT put decision logic in the markdown beyond this protocol.
  </action>
